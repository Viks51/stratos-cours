Le langage SQL (Structured Query Language) permet la définition de tables (création, modification ou suppression), la manipulation de données (extractions, ajouts, modifications ou suppressions de contenus) et leur protection (définition des permissions). Grâce à ce langage, le SI fournit aux différents acteurs d’une organisation des données précises, exhaustives et à jour. Les instructions de traitement formulées en SQL sont des requêtes, autrement dit des demandes de traitement. Comment extraire et mettre à jour les données à l’aide de requêtes SQL ?

À quoi ça sert ?

C’est le chapitre le plus directement employable de tout le programme. Un jour, un dirigeant vous demandera « combien nous ont acheté les clients de la région, l’an dernier ? » — et la réponse ne sera nulle part. Elle existera dans la base, répartie sur quatre tables, et il faudra aller la chercher.

SQL est le langage qui permet de le faire soi-même, sans passer par le service informatique ni attendre trois semaines. Un gestionnaire capable d’écrire une requête n’est plus tributaire des états que quelqu’un d’autre a prévus pour lui.

À l’examen, on vous demandera d’écrire des requêtes et d’en lire. Ce sont deux exercices différents : lire s’apprend en quelques heures, écrire seulement en écrivant.

Comment travailler ce chapitre

Tout le chapitre interroge une seule base : celle de Menuiseries Vasseur, reproduite en entier sur la page La base de données Menuiseries Vasseur. Six tables, une soixantaine de lignes.

Chaque requête de ce chapitre est exécutable dans la page. Sous chacune, un bouton Exécuter lance la requête pour de bon, et Modifier vous laisse la réécrire. Rien à télécharger, rien à installer : le moteur SQL tourne dans votre navigateur.

C’est ainsi qu’il faut lire ce chapitre : ne croyez aucun résultat, exécutez-le. Puis modifiez la requête, cassez-la, regardez le message d’erreur, recommencez. On n’apprend pas à écrire du SQL en lisant du SQL.

Le résultat de chaque requête est aussi imprimé dans le cours, sous forme de tableau. Il vous sert de corrigé, et il reste là si vous lisez hors ligne ou si le moteur ne se charge pas.

La base vit dans votre navigateur

Vous pouvez tout casser : UPDATE sans WHERE, DELETE de toute une table. Rien n’est partagé, rien n’est enregistré. Un bouton « Réinitialiser la base » remet les données d’origine, et recharger la page suffit aussi.

Une seule base sert à tout le chapitre, celle de Menuiseries Vasseur : les exemples du cours, les « Votre tour » et les cas pratiques l’interrogent tous.

2.3.1 Lire une base de données

Chez Vasseur — la situation

Sofiane Belkacem a besoin du chiffre d’affaires réalisé avec les collectivités sur l’exercice. Le logiciel de gestion commerciale propose 40 états préprogrammés ; aucun ne fait exactement cela.

Il demande donc l’extraction à l’éditeur, qui la facture 380 € et l’annonce sous trois semaines. Entre-temps, le conseil d’administration aura eu lieu.

La question de cette section : de quoi une base de données est-elle faite, et quel langage permet de lui poser une question qui n’était pas prévue ?

Le SGBD et le langage SQL

  • Le SGBD est un intermédiaire entre le programme et les données ;
  • Chaque SGBD utilise un langage afin de communiquer avec les applications qui souhaitent accéder aux données.

À savoir

Chaque SGBDR a sa propre manière d’interpréter le SQL. Heureusement, les fonctionnalités de base sont communes : le langage SQL présenté ici s’applique à tous les SGBDR. Mais il arrive que certains SGBDR ne prennent pas en charge certaines fonctionnalités plus avancées, ou bien que la syntaxe du SQL diffère légèrement d’un SGBDR à l’autre.

  • Parler en langage SQL, c’est formuler des requêtes à la base de données ;
  • Une requête peut avoir plusieurs buts : accéder à une donnée, ajouter une donnée, modifier la structure des tables, etc. ;
  • Les requêtes se répartissent en trois groupes :
Groupe — qui s’en sertCe qu’il faitMots clés
LDD — langage de définition de données
L’informaticien		Crée ou supprime des objets dans la base : tables, contraintesCREATE, ALTER, DROP
LCD — langage de contrôle de données
L’administrateur		Gère les utilisateurs et leurs droits sur les objetsGRANT, REVOKE
LMD — langage de manipulation de données
Le gestionnaire — vous		Manipule les lignes des tables : les créer, les lire, les modifier, les supprimerINSERT, SELECT, UPDATE, DELETE

Ce que le programme attend de vous

Le LMD, et lui seul. Vous n’aurez ni à créer des tables, ni à distribuer des droits : vous aurez en permanence à extraire des chiffres, et parfois à mettre à jour des données. C’est la répartition des responsabilités vue en 1.2 — la structure et les droits relèvent de la DSI, l’exploitation des données relève du métier.

Et le résultat d’une requête ?

Il s’affiche à l’écran, mais il peut aussi s’exporter. Tous les SGBD savent enregistrer un résultat dans un fichier que le tableur ouvrira, le plus souvent au format CSV : du texte, une ligne par enregistrement, les valeurs séparées par un point-virgule. C’est le chemin le plus courant entre la base et le tableur : on extrait par une requête, on analyse dans le tableur.

Le fichier exporté est une photographie : il ne se met pas à jour quand la base change. Le chapitre 2.6 montre l’autre sens, l’importation dans le tableur, qui peut conserver le lien avec la source.

La base sur laquelle nous allons travailler

  • Menuiseries Vasseur a fini par se doter d’une vraie base de données, construite selon les règles des chapitres 2.1 et 2.2 ;
  • Elle compte six tables, reproduites en entier sur la page La base de données Menuiseries Vasseur :
CLIENT     (id_client, nom_client, categorie, ville, date_creation)
CHANTIER   (id_chantier, #id_client, ville_chantier, date_debut, date_fin, montant_ht)
PRODUIT    (ref_produit, designation, matiere, prix_ht)
POSER      (#id_chantier, #ref_produit, quantite)
SALARIE    (id_salarie, nom_salarie, prenom_salarie, fonction, site, date_embauche)
INTERVENIR (#id_chantier, #id_salarie, date_intervention, nb_heures)

Le geste à prendre : lire le schéma avant d’écrire

On n’interroge pas une base dont on ne connaît pas la structure. Avant toute requête, on regarde le schéma et on répond à trois questions :

  1. Où est l’information que je cherche ? Dans quelle table, dans quelle colonne ?
  2. De quelles autres tables ai-je besoin ? Le nom du client n’est pas dans CHANTIER : il faudra aller le chercher ;
  3. Par quel chemin les relier ? Quelle clé étrangère mène à quelle clé primaire ?

Un étudiant qui saute cette étape écrit des requêtes syntaxiquement correctes et logiquement fausses. C’est l’erreur la plus fréquente, et la plus coûteuse en points.

Les clés primaires

Rappel

La clé primaire identifie de façon unique et certaine chaque ligne d’une table. Elle ne peut jamais être nulle, et deux lignes ne peuvent pas porter la même valeur.

  • Dans la base de Menuiseries Vasseur, les six clés primaires sont :
TableClé primaireType
CLIENTid_clientSimple
CHANTIERid_chantierSimple
PRODUITref_produitSimple
SALARIEid_salarieSimple
POSER(id_chantier, ref_produit)Composée
INTERVENIR(id_chantier, id_salarie, date_intervention)Composée

Pourquoi cela vous concerne dès maintenant

Connaître la clé primaire d’une table permet de prévoir le nombre de lignes qu’une requête va renvoyer. C’est le seul garde-fou dont vous disposiez : une requête qui renvoie beaucoup plus de lignes que prévu est une requête fausse, même si elle affiche des chiffres crédibles.

Exemple : CHANTIER compte 10 lignes et id_chantier en est la clé primaire. Une requête qui part de CHANTIER et rapproche CLIENT ne peut pas renvoyer plus de 10 lignes. Si elle en renvoie 80, la condition de rapprochement manque.

Mettre en relation plusieurs tables avec des clés étrangères

Rappel

Une clé étrangère est un attribut qui reprend la clé primaire d’une autre table, afin de relier les deux. Elle est notée avec un dièse dans le schéma relationnel.

  • La base compte cinq clés étrangères :
Clé étrangèreCe que cela veut dire
#id_client dans CHANTIER → CLIENT.id_clientChaque chantier appartient à un client
#id_chantier dans POSER → CHANTIER.id_chantierChaque ligne de pose concerne un chantier
#ref_produit dans POSER → PRODUIT.ref_produit…et un produit
#id_chantier dans INTERVENIR → CHANTIER.id_chantierChaque intervention concerne un chantier
#id_salarie dans INTERVENIR → SALARIE.id_salarie…et un salarié

Une image pour comprendre

Une clé étrangère, c’est le numéro de dossier porté sur un document. Le chantier 105 ne recopie pas l’identité complète de Constructions Ligéria : il porte le numéro 4, et c’est ce numéro qui permet d’aller chercher le reste.

Toute la puissance du modèle tient là : le nom du client est écrit une seule fois, et dix chantiers peuvent y renvoyer.

Suivez le chemin à la main

Question : qui est le client du chantier n° 106 ?

  1. Dans CHANTIER, la ligne 106 porte id_client = 4 ;
  2. Dans CLIENT, l’identifiant 4 est Constructions Ligéria, promoteur à Tours.

Vous venez d’exécuter une jointure. Le SQL ne fait rien d’autre — il le fait simplement sur 10 000 lignes sans se tromper.

Identifier les types d’associations entre les tables

Le piège du chemin manquant

Il n’existe aucun lien direct entre CLIENT et PRODUIT. Pour répondre à « quels produits Rivière & Fils a-t-il commandés ? », il faut parcourir trois liens :

CLIENT ──▶ CHANTIER ──▶ POSER ──▶ PRODUIT

Soit trois jointures. Les étudiants cherchent souvent une clé étrangère qui n’existe pas, puis renoncent. Le réflexe à installer : tracer le chemin sur le schéma avant d’écrire la première ligne.

Chez Vasseur — la réponse

De quoi une base de données est-elle faite, et quel langage permet de lui poser une question qui n’était pas prévue ?

Elle est faite de tables, reliées par des clés étrangères — exactement ce qu’a construit le chapitre 2.1. Ce qui change ici, c’est qu’on ne la conçoit plus : on l’interroge.

Le langage est SQL, et il se répartit en trois familles : le LDD crée la structure, le LCD gère les droits, le LMD manipule les données. C’est le troisième qui vous concerne, et principalement son verbe SELECT.

Pour Sofiane Belkacem, cela signifie qu’il n’a pas besoin de l’éditeur. Son chiffre d’affaires par catégorie de clients tient en une requête :

Vous ne savez pas encore l’écrire — c’est l’objet des deux sections suivantes. Mais vous pouvez déjà en lire la structure : prendre les chantiers, aller chercher le client de chacun, regrouper par catégorie, additionner les montants. Les 380 € et les trois semaines payaient l’absence de cette compétence, pas une difficulté technique.

La condition préalable, en revanche, est réelle : on ne peut pas interroger une base dont on ne connaît pas la structure. D’où l’ordre de ce chapitre — comprendre les tables et leurs liens avant d’écrire la première requête.

Vérifiez que vous avez compris

À quelle famille appartiennent SELECT, CREATE TABLE et GRANT ? Laquelle vous concerne en tant que gestionnaire ?

SELECT relève du LMD (langage de manipulation de données), CREATE TABLE du LDD (langage de définition de données), GRANT du LCD (langage de contrôle de données).

Celle qui vous concerne est le LMD. Vous n’aurez ni à créer des tables, ni à distribuer des droits ; vous aurez en permanence à extraire des chiffres et, plus rarement, à corriger des données. C’est aussi la répartition des responsabilités vue en 1.2 : la structure et les droits relèvent de la DSI, l’exploitation des données relève du métier.

Votre tour

Avant de passer aux requêtes, prenez la main sur la base. Modifiez le nom de la table, ajoutez un WHERE, faites une faute de frappe volontaire pour voir ce que répond le moteur.

2.3.2 Construire des requêtes simples

Chez Vasseur — la situation

Élodie Fournier veut la liste des chantiers de plus de 50 000 €, avec le nom du client — pas son numéro, son nom.

Les montants sont dans la table CHANTIER. Les noms sont dans la table CLIENT. Les deux ne se rencontrent nulle part sur un écran.

La question de cette section : comment choisir les colonnes, ne garder que les lignes utiles, et faire dialoguer deux tables ?

Afficher les données pertinentes avec SELECT

  • SELECT répond à la question « quelles colonnes ? ». C’est la projection ;
  • La forme minimale d’une requête comporte deux clauses : SELECT (quelles colonnes) et FROM (dans quelle table).

L’étoile est commode, pas recommandable

SELECT * sert à explorer une table qu’on découvre. Elle n’a pas sa place dans une requête destinée à produire un état :

  • elle ramène des colonnes dont on n’a pas besoin, et rend le résultat illisible ;
  • elle transporte des données inutiles sur le réseau — sur une table de 200 000 lignes, la différence est mesurable ;
  • elle casse silencieusement le jour où quelqu’un ajoute une colonne : tout ce qui repose sur la position des colonnes se décale.

Sur une copie d’examen, SELECT * là où l’énoncé nomme les informations attendues coûte des points.

DISTINCT porte sur la ligne entière

SELECT DISTINCT designation, matiere FROM produit renverrait les huit lignes, puisque chaque couple (désignation, matière) est unique. DISTINCT ne dédoublonne pas colonne par colonne : il dédoublonne le résultat complet. C’est une erreur d’interprétation classique.

Un calcul dans un SELECT ne modifie rien

La colonne prix_ttc n’existe pas dans la base : elle est calculée à l’affichage, le temps de la requête. La table PRODUIT n’est pas modifiée. C’est la même logique qu’une formule de tableur — et c’est aussi la raison pour laquelle on ne stocke pas les données calculées, comme l’a établi le chapitre 2.1.

Récupérer des données issues de plusieurs tables

La demande d’Élodie Fournier suppose deux tables : les montants sont dans CHANTIER, les noms dans CLIENT. Que se passe-t-il si l’on nomme simplement les deux ?

Le résultat compte 80 lignes — 8 clients × 10 chantiers. Chaque client a été associé à tous les chantiers, y compris ceux qui ne sont pas les siens.

Définition

Le produit cartésien associe chaque ligne de la première table à chaque ligne de la seconde. Son nombre de lignes est le produit des deux effectifs.

Une image pour comprendre

C’est un plan de table dressé au hasard : on a bien tous les invités et toutes les chaises, mais personne n’est assis à sa place. L’information est là, noyée dans 80 combinaisons dont 70 n’ont aucun sens.

Sur une vraie base, ce n’est pas anecdotique

8 × 10 fait 80. Mais une table de clients de 5 000 lignes et une table de commandes de 40 000 lignes font 200 millions de lignes. Un produit cartésien involontaire fige le serveur — et c’est la première cause de requête qui « ne rend jamais la main ».

Le garde-fou : comptez avant de lancer. Vous connaissez la taille de vos tables ; vous savez donc ce que vous risquez.

Lier des tables avec une jointure interne

Il faut donc filtrer ce produit cartésien pour ne garder que les combinaisons cohérentes : celles où l’identifiant du client du chantier est bien celui du client. C’est ce qu’on appelle une jointure.

Définition

Une jointure est le rapprochement de deux tables selon une condition de jointure, qui met le plus souvent en regard la clé étrangère de l’une et la clé primaire de l’autre.

Techniquement : un produit cartésien, suivi d’un filtrage.

La syntaxe à écrire : INNER JOIN … ON

Dix lignes, et non 80. On est passé du produit cartésien au résultat utile.

Trois points de syntaxe à acquérir tout de suite

  • Les alias : chantier ch et client c donnent un nom court à chaque table. Ils rendent la requête lisible dès qu’il y a plus de deux tables ;
  • Le préfixage : ch.id_client et c.id_client s’appellent pareil dans les deux tables. Sans préfixe, le SGBD refuse la requête pour ambiguïté ;
  • ON porte la condition de rapprochement, et elle seule. Les conditions de filtrage métier restent dans le WHERE.

L’ancienne syntaxe, que vous rencontrerez

La forme FROM chantier ch, client c WHERE ch.id_client = c.id_client produit exactement le même résultat : c’est l’écriture d’avant la norme SQL-92, et elle reste valable dans tous les SGBD.

Vous devez savoir la lire, parce qu’une grande partie du code existant l’emploie. Mais ne l’écrivez pas, pour trois raisons :

  • elle mélange dans le WHERE les conditions de jointure et les conditions de filtrage métier, qui n’ont rien à voir ;
  • oublier la condition ne produit pas une erreur, mais un produit cartésien silencieux ;
  • elle ne sait pas exprimer les jointures externes, qui n’existent qu’en syntaxe JOIN … ON.

Retenez la règle : le ON dit comment les tables se rejoignent, le WHERE dit quelles lignes on garde.

Combien de lignes peut renvoyer une jointure ?

  • Chaque chantier possède au plus un client — id_client est une clé étrangère qui pointe vers une clé primaire, laquelle est unique par définition ;
  • Le résultat contient donc au plus autant de lignes que CHANTIER, soit dix.

La règle qui vous sauvera

Quand on joint une clé étrangère d’une table A vers la clé primaire d’une table B, le résultat contient au plus autant de lignes que A.

Ce simple décompte détecte la quasi-totalité des jointures fausses. Si vous partez de 10 chantiers et que vous en obtenez 80, la condition manque ; si vous en obtenez 4, vous avez perdu des lignes en route.

Joindre sur une seule des deux colonnes d’une clé composée ne provoque aucune erreur : cela produit un résultat trop grand, où chaque ligne est multipliée. Une clé étrangère reprend l’intégralité de la clé primaire visée.

Maîtriser les jointures externes

Reprenons la première jointure. Elle renvoie dix lignes — une par chantier. Mais la table CLIENT en compte huit, et seuls sept apparaissent dans le résultat.

C’est le défaut le plus dangereux du chapitre

Une jointure interne ne renvoie pas d’erreur quand elle perd des lignes. Elle renvoie un résultat plus court, d’apparence parfaitement normale.

Sur un état « chiffre d’affaires par client », les clients sans commande disparaissent — et personne ne saura qu’ils existent. Sur un état « salariés et leurs interventions », les salariés jamais affectés disparaissent. Ce sont précisément les lignes qu’on cherchait.

Le signal à repérer dans un énoncé

Dès qu’une question contient « y compris ceux qui… », « même si… », « tous les… » ou « et ceux qui n’en ont pas », il faut une jointure externe. C’est presque un automatisme, et cela vaut plusieurs points à l’examen.

La jointure naturelle

NATURAL JOIN effectue la jointure automatiquement sur toutes les colonnes portant le même nom dans les deux tables.

À connaître, à ne pas employer

Elle paraît commode, mais elle est dangereuse : elle dépend entièrement du nommage des colonnes. Le jour où quelqu’un ajoute à CLIENT une colonne ville_chantier, ou renomme une colonne, la jointure change de sens sans que la requête ait été touchée.

Sachez la reconnaître si vous la croisez ; écrivez INNER JOIN … ON, qui dit explicitement sur quoi porte le rapprochement.

Chez Vasseur — la réponse

Comment choisir les colonnes, ne garder que les lignes utiles, et faire dialoguer deux tables ?

Trois clauses, et une seule requête :

  • SELECT répond à quelles colonnes ? — c’est la projection. On nomme les colonnes voulues plutôt que d’écrire * ;
  • WHERE répond à quelles lignes ? — c’est la restriction, avec AND, OR, IN, BETWEEN, LIKE, IS NULL ;
  • INNER JOIN … ON répond à quelles tables, rapprochées comment ? — c’est la jointure, qui met en regard la clé étrangère de l’une et la clé primaire de l’autre.

La demande d’Élodie Fournier tenait en une phrase française ; elle tient en quatre lignes de SQL. Et le mécanisme sous-jacent explique les accidents : une jointure est un produit cartésien suivi d’un filtrage. Oubliez la condition, et vous n’obtenez pas une erreur — vous obtenez les 80 combinaisons, silencieusement.

Reste le piège dont il faut se souvenir toute sa vie professionnelle : INNER JOIN fait disparaître ce qui n’a pas de correspondance. SCI Le Clos n’apparaît pas dans le résultat, et rien ne le signale. Si la question avait été « quel est le chiffre d’affaires de chaque client ? », ce client aurait purement et simplement manqué à l’appel. Les jointures externes existent pour cela, et l’énoncé les réclame chaque fois qu’il dit « tous les » ou « y compris ceux qui ».

Vérifiez que vous avez compris

Vous écrivez une jointure entre CLIENT (8 lignes) et CHANTIER (10 lignes), et le résultat en compte 80. Que s’est-il passé ?

La condition de jointure manque, ou elle est fausse. 8 × 10 = 80 : c’est très exactement le produit cartésien, chaque client ayant été associé à tous les chantiers.

Le réflexe à acquérir : devant un résultat anormalement gros, comptez. Une jointure d’une clé étrangère vers une clé primaire ne peut pas produire plus de lignes que la table portant la clé étrangère — ici, dix au maximum.

Et devant un résultat anormalement petit, comptez aussi : c’est le signe inverse, celui d’une jointure interne qui a écarté des lignes sans correspondance.

Confusion très fréquente, et sanctionnée :

  • une jointure ajoute des colonnes — elle met deux tables côte à côte ;
  • une UNION ajoute des lignes — elle empile deux résultats.

Le test : « ai-je besoin de plus d’informations sur chaque ligne, ou de plus de lignes ? »

Imbriquer une requête dans une autre : les sous-requêtes

Camille Vasseur pose une question simple : « quels chantiers dépassent notre montant moyen ? » Le réflexe consiste à écrire WHERE montant_ht > AVG(montant_ht), et le SGBD refuse, pour la raison déjà vue avec HAVING : une fonction d’agrégation n’a pas sa place dans un WHERE.

La solution consiste à faire calculer la moyenne d’abord, par une requête à part, puis à utiliser son résultat dans la requête principale.

Définition

Une sous-requête est une requête SELECT écrite entre parenthèses à l’intérieur d’une autre requête. Le SGBD l’exécute en premier, puis se sert de son résultat comme d’une valeur ou d’une liste.

Une sous-requête de ce type s’emploie derrière un opérateur de comparaison : =, <>, >, <, >=, <=.

Une valeur ou une liste ?

  • Derrière =, >, <…, la sous-requête doit renvoyer une seule valeur. Si elle en renvoie plusieurs, la plupart des SGBD refusent la requête.
  • SQLite, le moteur de la console, ne la refuse pas : il prend la première valeur et ne dit rien. WHERE id_client = (SELECT id_client FROM chantier WHERE date_fin IS NULL) ne renvoie que Rivière & Fils, alors que quatre clients sont concernés. C’est plus dangereux qu’une erreur.
  • Dès que la sous-requête peut renvoyer plusieurs lignes, employez IN ou NOT IN.

La méthode

  1. Écrivez et exécutez d’abord la sous-requête seule, et vérifiez son résultat.
  2. Placez-la entre parenthèses, derrière IN ou derrière un opérateur de comparaison.
  3. Relisez le besoin : « les … qui figurent parmi … » appelle un IN ; « au-dessus de la moyenne », « le plus cher » appellent une comparaison à une sous-requête qui calcule un agrégat.

Comment passer du détail au chiffre agrégé, et comment filtrer sur ce chiffre agrégé ?

Par GROUP BY, et par la clause qui lui est propre, HAVING :

Camille Vasseur obtient son tableau : promoteurs 370 850 €, collectivités 87 400 €, les particuliers écartés à 41 350 €.

Le seul vrai obstacle du chapitre tient en une phrase : WHERE et HAVING ne filtrent pas la même chose. Le premier écarte des lignes de détail avant le regroupement ; le second écarte des groupes après. Une condition portant sur une fonction d’agrégation va toujours dans le HAVING ; toute autre condition va dans le WHERE.

Second point de vigilance : dans une requête avec GROUP BY, le SELECT ne peut contenir que les colonnes de regroupement et des fonctions d’agrégation. Demander le nom d’un client à côté d’une somme par catégorie n’a pas de sens.

Et l’ordre d’écriture des clauses, à retenir tel quel :

SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY

Vérifiez que vous avez compris

« Le nombre de chantiers par ville, pour les seules villes en comptant plus de deux, et uniquement les chantiers terminés. » Où va chacune des deux conditions ?

  • « chantiers terminés » porte sur une ligne de détail — chaque chantier a, ou n’a pas, une date de fin. Elle va dans le WHERE, avant regroupement ;
  • « plus de deux chantiers » porte sur le groupe — c’est un COUNT. Elle va dans le HAVING, après regroupement.

Sur cette base, le résultat est vide : aucune ville ne compte plus de deux chantiers terminés. Un résultat vide n’est pas une erreur — c’est une réponse, et il faut savoir le dire plutôt que de « corriger » la requête jusqu’à ce qu’elle rende quelque chose.

Notez enfin l’ordre des opérations : on écarte d’abord les chantiers en cours, puis on compte. L’inverse donnerait un tout autre résultat.

  3. les villes où l’entreprise a réalisé plus de 50 000 € de chantiers ;

UPDATEModifie la valeur de colonnes sur des lignes existantesInchangé
DELETE FROMSupprime des lignesDiminue

Avant toute chose

Ces trois requêtes modifient la base. Contrairement à un SELECT, elles ne sont pas rejouables sans conséquence, et il n’y a pas d’annulation.

La règle professionnelle, à appliquer sans exception : écrivez d’abord la requête en SELECT. Si le SELECT renvoie exactement les lignes que vous vouliez toucher, remplacez-le par UPDATE ou DELETE. C’est la seule protection réellement efficace, et elle ne coûte que dix secondes.

Trois points de vigilance

  • Nommez les colonnes. INSERT INTO client VALUES (…) fonctionne, mais dépend de l’ordre physique des colonnes : le jour où quelqu’un en ajoute une, toutes vos insertions deviennent fausses sans erreur visible ;

L’erreur qui coûte cher

Un UPDATE sans WHERE modifie toutes les lignes de la table.

Aucun message, aucune confirmation : la requête réussit. C’est l’accident le plus fréquent, et le plus difficile à rattraper — le prix d’origine n’existe plus nulle part.

Le WHERE n’est pas facultatif dans la pratique : il est facultatif pour le SGBD, jamais pour vous.

Supprimer des lignes : DELETE FROM

Sur cette base, la requête ne supprime aucune ligne : tous les chantiers sont postérieurs à 2020. Un DELETE qui ne supprime rien n’est pas une erreur — c’est un DELETE dont la condition n’a trouvé personne.

Les deux pièges de DELETE

  • DELETE FROM produit ; vide la table entière. Même remarque que pour UPDATE, avec des conséquences pires : les lignes sont perdues ;
  • L’intégrité référentielle peut bloquer la suppression — et c’est heureux. Supprimer le client 1 laisserait les chantiers 101 et 102 rattachés à un client inexistant. Le SGBD refuse, et il a raison : la réponse n’est pas de forcer, mais de se demander si l’on veut vraiment supprimer, ou plutôt désactiver.

Supprimer ou désactiver ?

En gestion, la suppression est presque toujours le mauvais réflexe. Un client qui ne commande plus n’a pas disparu : ses chantiers, ses factures et son historique doivent rester justifiables — c’est une exigence de piste d’audit (voir 1.4).

La bonne pratique consiste à ajouter une colonne actif et à écrire UPDATE client SET actif = 0 WHERE … plutôt que DELETE. On parle de suppression logique, par opposition à la suppression physique.

Une image pour comprendre

SELECT, c’est consulter le dossier. UPDATE, c’est corriger une ligne au stylo. DELETE, c’est passer le dossier au broyeur.

On relit toujours avant de corriger. On relit deux fois avant de broyer. Et dans un cabinet comptable, on ne broie pratiquement jamais : on archive.

Chez Vasseur — la réponse

Comment modifie-t-on des données en masse, et comment ne pas détruire la base en le faisant ?

Les références en aluminium tiennent en une requête, et la soirée de Nadia Perrot est terminée :

Mais la requête ne s’écrit pas en premier. La méthode compte plus que la syntaxe, et elle tient en quatre gestes :

  1. Compter d’abord. SELECT COUNT(*) FROM produit WHERE matiere = 'aluminium' ; doit renvoyer 5. Si le chiffre diffère, le WHERE est faux — et il aurait été faux dans l’UPDATE aussi ;
  2. Regarder ensuite. Le même WHERE en SELECT * montre exactement les lignes qui vont bouger ;
  3. Remplacer le verbe. SELECT devient UPDATE, le WHERE ne bouge plus ;
  4. Vérifier après. Le SGBD annonce le nombre de lignes affectées : il doit dire 5.

Trois erreurs à ne jamais commettre, dans l’ordre de gravité : un UPDATE sans WHERE (toute la table), un DELETE à la place d’un UPDATE (irréversible), et une modification en masse sans sauvegarde préalable en production.

Et le point de gestion, qui dépasse la technique : cette augmentation de 4 % écrase les anciens prix. Si l’entreprise doit pouvoir justifier le prix appliqué à un chantier de mars, il ne faut pas modifier le tarif — il faut en historiser un nouveau, avec sa date d’effet. C’est très exactement la leçon du chapitre 2.2.

Vérifiez que vous avez compris

Un collègue vous dit : « j’ai lancé un UPDATE, il a modifié 4 000 lignes au lieu de 12 ». Que s’est-il passé, et que fallait-il faire ?

Son WHERE était trop large — ou absent. La requête a fait exactement ce qu’on lui demandait ; c’est la condition qui ne décrivait pas les 12 lignes voulues.

Il fallait écrire la requête en SELECT d’abord : SELECT * FROM … WHERE … aurait affiché 4 000 lignes, et l’erreur aurait sauté aux yeux avant toute modification.

Et maintenant ? Si une transaction est ouverte, ROLLBACK. Sinon, seule une sauvegarde permet de revenir en arrière — d’où l’importance de la fonction « sécuriser » du SI, vue en 1.1, qui cesse d’être une abstraction le jour où l’on en a besoin.

Votre tour

Ici, allez-y franchement : c’est la seule section où l’erreur est instructive.

  1. augmentez de 10 % le prix des produits en PVC, puis vérifiez le résultat ;
  2. lancez volontairement un UPDATE sans WHERE et regardez le nombre de lignes affectées ;
  3. réinitialisez la base, puis recommencez proprement.

Avec imbrication : la sous-requête

FormeQuand l’employerExemple sur la base Vasseur
WHERE champ > (SELECT agrégat …)Comparer chaque ligne à un chiffre calculé : moyenne, maximum…WHERE montant_ht > (SELECT AVG(montant_ht) FROM chantier)

Les trois distinctions qui font la différence à l’examen

  • WHERE filtre des lignes, HAVING filtre des groupes. Toute condition portant sur SUM, COUNT, AVG, MIN, MAX va dans le HAVING ;
  • ON rapproche, WHERE sélectionne. Ne mettez jamais une condition de jointure dans le WHERE ;
  • INNER JOIN perd les lignes sans correspondance, LEFT JOIN les conserve. Un « et ceux qui n’en ont pas » dans l’énoncé impose une jointure externe.

RIGHT OUTER JOINToutes les lignes de la table de droite, appariées ou non
FULL OUTER JOINToutes les lignes des deux tables

Les opérateurs du WHERE

= · <> · < · > · <= · >= · BETWEEN … AND … · IN (…) · LIKE 'A%' · IS NULL · IS NOT NULL — combinés par AND, OR, NOT.

NULL ne se compare pas

WHERE date_fin = NULL ne renvoie jamais rien. Il faut IS NULL ou IS NOT NULL. C’est l’une des erreurs les plus fréquentes, et elle ne provoque pas de message : elle renvoie un résultat vide.

La méthode, en quatre gestes

  1. Compter : SELECT COUNT(*) FROM … WHERE … — le chiffre est-il celui attendu ?
  2. Regarder : le même WHERE en SELECT * — sont-ce les bonnes lignes ?
